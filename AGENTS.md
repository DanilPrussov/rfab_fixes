# Инструкции для агентов

## Назначение и окружение

- Здесь разрабатываются небольшие исправления Skyrim RFAB для последующего
  включения авторами в сборку. Общаться и писать документацию по-русски;
  идентификаторы каталогов — ASCII, lowercase kebab-case.
- Рабочая платформа — macOS. Не планировать компиляцию DLL, замену SKSE DLL
  или разработку нативных плагинов в рамках текущего направления.
- MO2 находится в `/Users/danilprusov/Downloads/kazan/MO2`.
  Использовать как источник для чтения. Изменять установленную сборку только
  когда это входит в конкретное задание пользователя на установку/проверку.
  Уже данное разрешение повторно не запрашивать.
- Данные об окружении: `docs/ENVIRONMENT.md`. Известный профиль — `Default`;
  перед новой диагностикой проверять актуальные настройки.
- Не считать запуск Python-проверок доказательством работоспособности в игре.
  Не утверждать, что Skyrim, MO2, xEdit или Creation Kit запускались, если
  фактического запуска и результата нет.

## Организация задачи

- Один самостоятельный баг — `fixes/NNNN-short-name/`; следующий свободный
  номер выбирается после просмотра существующих каталогов. Создавать через
  `python3 tools/fix.py new NNNN-short-name`.
- Перед изменением прочитать README, TESTING, UPSTREAM существующего фикса.
  Узкие правила отдельной задачи можно записать в её локальный `AGENTS.md`,
  когда такие правила действительно появились.
- В README поддерживать статус: `draft`, `ready-for-test`, `verified`,
  `submitted`, `integrated`. При блокировке записывать причину и следующий шаг.
  Не повышать статус без соответствующего результата.
- В `payload/` хранить только необходимые для установки файлы, с путями
  относительно Skyrim `Data`. Не добавлять внешний каталог `Data`, исходный
  мод целиком, сохранения, логи, `meta.ini` MO2 или документацию задачи.
- В `src/` хранить нужные для воспроизводимости исходники/преобразования,
  в `evidence/` — небольшие относящиеся к багу материалы. Большие исходные
  копии и полные логи помещать в игнорируемый `scratch/<fix-id>/`.
- Не смешивать с исправлением балансные изменения, рефакторинг и соседние
  баги. Независимые изменения оформлять отдельно.

## Диагностика и правки

- До правки определить исходный мод, профиль, путь ресурса относительно Data,
  SHA-256 исходных байтов и версии затронутых компонентов. Неизвестное
  явно обозначать; не выводить версию RFAB/Skyrim из версии MO2.
- Проверить `profiles/<profile>/modlist.txt`, `plugins.txt`, `loadorder.txt`
  и `overwrite/` в объёме, необходимом для задачи. Учитывать других
  поставщиков того же ресурса и ресурсы в архивах. Если фактический победитель
  не установлен локально, пометить это и проверить в MO2 на Windows.
- Различать приоритет файлов модов и порядок ESP/ESM/ESL. Не сортировать
  сборку и не «чистить» плагины автоматически.
- Сохранять кодировку, BOM, переводы строк, регистр путей и формат исходника.
  Не прогонять массовое форматирование через чужие игровые файлы.
- Для конфигов учитывать конкретного потребителя: INI не имеет единой
  строгой схемы, JSON может быть диалектом. Проверять ключи, placeholders,
  идентификаторы и ссылки, а не только успешный разбор парсером.
- Не применять hex-правки к ESP/ESM/ESL/PEX/SWF/NIF/HKX. Использовать
  специализированный проверенный маршрут, если такой тип задачи принят.
- Papyrus `.psc` можно исследовать и готовить как исходник в `src/`, но
  работающий скриптовый фикс требует соответствующего `.pex`.
  Пока нет проверенного способа компиляции и игрового теста, это исходный
  патч с явным ограничением, а не готовое исправление для игры.
- Локальные копии файлов установленной сборки использовать для разработки
  и тестовой упаковки. При внешней передаче ресурса с неизвестными условиями
  распространения готовить минимальный diff или рецепт интеграции.
  Не переносить лицензию проекта автоматически на содержимое чужих модов.

## Проверка и передача

- В `TESTING.md` разделять выполненные локальные проверки и ещё требуемые
  проверки на Windows. Указывать дату, команды/шаги, среду и результат.
- Сначала подтвердить симптом на базовой сборке, затем результат с фиксом.
  Предусмотреть смежный сценарий, установку, зависимости и откат.
  Сохранения для сравнения брать из копии до установки; не обещать безопасное
  удаление скриптового/плагинного фикса из уже изменённого сохранения.
- Запускать проверки форматов и структуры, относящиеся к изменению.
  Для инструментов проекта использовать `python3 -m unittest discover -s tests`.
  Не писать тесты, которые только повторяют содержимое простого конфига.
- Перед упаковкой выполнить `check`, затем `package`. Успешная упаковка
  подтверждает структуру архива, а не игровую совместимость и не лицензию.
- В `UPSTREAM.md` перечислить файлы, объяснить причину, указать базу/хеши,
  зависимости, расположение в MO2, результаты проверки и способ интеграции
  в исходный мод. Если несколько фиксов заменяют один файл, явно описать
  совместимость и способ объединения.
- Внешнюю отправку, публикацию и сообщения авторам делать только по
  поручению пользователя. Самостоятельно готовить весь пакет к передаче.
- В финальном ответе назвать изменённые файлы, выполненные проверки,
  оставшиеся ограничения и ближайший необходимый шаг.
