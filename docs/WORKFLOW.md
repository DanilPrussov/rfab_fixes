# Разработка и включение в RFAB

## 1. Карточка и исходная база

Создать каталог через `tools/fix.py new`. В README записать симптом,
ожидаемое поведение, воспроизведение и критерий успеха. Сначала выяснить,
это ошибка сборки, персональных настроек или конкретного сохранения.

Записать версию RFAB и Skyrim runtime, профиль, версии затронутых модов.
Если версии неизвестны, оставить это явным ограничением. Для каждого исходного
файла записать путь от MO2, Data-путь и SHA-256, например:

```sh
shasum -a 256 "/полный/путь/к/исходному/файлу"
```

Проверить, что именно этот ресурс выигрывает конфликты. В местной копии есть
непустой `overwrite/`, поэтому наличие файла в `mods/RFAB` само по себе
не доказывает, что игра его использует.

## 2. Минимальное исправление

Скопировать в `payload/` только заменяемые файлы, сохранив Data-пути.
Новые конфиги создавать отдельным файлом лишь там, где потребитель действительно
поддерживает такую загрузку. Не придумывать формат расширения ради удобства.

Пояснить причину и изменение в README. Небольшой diff или преобразование
помогают авторам встроить изменение даже после обновления большого исходного
файла. Сохранять чужие кодировки и окончания строк; исключить случайный шум.

## 3. Проверка на Mac

Проверить подходящим способом структуру, синтаксис, ключи, ссылки, регистр,
кодировку и минимальность diff. Выполнить `tools/fix.py check`.
Для исправлений данных проверять и смысл значений: успешный JSON-разбор
не подтверждает, что плагин понимает эти настройки.

Записать точные результаты в TESTING. При готовом кандидате перевести статус
в `ready-for-test`, затем сделать ZIP через `package`. Этот архив предназначен
для проверки; `verified` пока не ставить.

## 4. Проверка в игре

На Windows установить ZIP отдельным модом, например `RFAB Fix 0001 — название`.
Использовать отдельный тестовый профиль, явно проверить изоляцию сохранений
и наличие копии сохранения до установки.

Указать моды, файлы которых патч должен перекрывать. Для ESP/ESM/ESL отдельно
указать мастера и ожидаемый порядок плагинов. Проверить, что `overwrite/`
не перекрывает исправление. В MO2 поставщик одинакового файла определяется
[приоритетом модов и виден в Conflicts](https://github.com/ModOrganizer2/modorganizer/wiki/Mod-information-window#conflicts).

Выполнить одинаковые шаги на базе без патча и с патчем; проверить хотя бы
один связанный сценарий, который не должен сломаться. В TESTING записать
версию базы, хеш испытанного ZIP, условия, ожидаемый и фактический результат.
Если проверял пользователь, так и указать. После успеха — `verified`.

Для отката отключить мод и вернуться к копии сохранения до испытаний.
Дополнительные требования конкретного фикса описать отдельно.

## 5. Передача авторам

Довести UPSTREAM до самостоятельной инструкции: проблема, причина,
минимальная правка, совместимость, файлы, зависимости, тесты, инструкция
по переносу в исходный мод. Приложить архив или diff согласно правам на файлы.
Не распространять всю сборку и полные пользовательские логи.

Подготовка материалов выполняется в рамках разработки. Отправка происходит
по поручению пользователя. После фактической отправки — `submitted` со
ссылкой/датой; после подтверждённого включения — `integrated` с версией RFAB.
Старый отдельный мод отключают после проверки, что обновление сборки содержит
то же исправление: иначе он может перекрыть более новые данные.

## История изменений

Используем Git для небольших исходников, документации и файлов исправления.
Один самостоятельный фикс — отдельная ветка при необходимости и небольшие
логические коммиты. Полные копии модов и ZIP не коммитим.
Не объединяем фиксы, заменяющие один файл, простым порядком установки:
сначала выясняем, как сохранить обе правки.
